# Read submissions, not calendars, to auto-complete tasks

Apex Scholar can auto-mark a study task done when a student submits the matching Schoology assignment, but not from the iCal feed. It has to come from the signed REST API the app already proxies, and only after the app can legally reach students outside its own school. For dropbox-style assignments, Schoology returns the student's own submission revisions with `created`, `late` and `draft` flags, and "latest revision exists and is not a draft" is the rule Schoology Plus has used in production for its checkmarks. Tests, discussions, external tools and paper work have no revisions, so for those "a grade or exception appeared" is the only signal. The bigger blocker is policy. Since **June 25, 2025**, a Schoology app must be **approved by Schoology** before it can read users at other schools, and **OAuth1 tokens die after 90 days**, so today's Netlify flow probably works only for students at the developer account's own school. Canvas is harder. Every district's admin has to enable a developer key, and asking students to paste personal tokens is banned by Instructure's policy and is now often disabled. That leaves the iCal feed (dates only) or a browser-extension companion as Canvas's realistic near-term paths. Both platforms expose much more than the calendar: grades, grading categories and weights, courses, announcements and materials. The cost is approvals, SOPIPA-style privacy duties, and a real chance that districts block the feature. Grade calculators carry the most district hostility of anything here. The recommended order is to harden the existing Schoology proxy (including restricting it to GET plus `POST /multiget`), apply for Schoology App Center approval in parallel, ship Canvas iCal with manual check-off, and defer grade math and the extension until real student accounts confirm the open questions.

## Schoology submission data supports auto-complete for most assignments

The calendar feed is a dead end for completion. Neither the Schoology nor the Canvas iCal feed carries any submission state, and the Schoology feed is flaky on its own terms: it works only if the personal calendar has at least one entry, and Google Calendar takes up to 8 hours to refresh it ([McQuaid help](https://help.mcquaid.org/schoology/linking-calendars)). Completion has to come from the REST API.

The API supports it well for the most common case. `GET /v1/sections/{section_id}/submissions/{grade_item_id}/{user_id}` returns one user's revisions, newest first. Each revision carries `revision_id`, `created` ("The time the revision was submitted"), `late`, `num_items` and `draft`, and a user can hold only one active draft ([Submissions](https://developers.schoology.com/api-documentation/rest-api-v1/submissions/)). Schoology Plus's "assignment checkmarks" feature calls the older `dropbox/{assignmentId}/{userId}` alias. It marks an item complete when **revisions exist and the last one is not a draft**, and when the call errors it logs that the item is "likely not a normal assignment" and lets the user override by hand ([SchoologyPlus home.ts](https://github.com/aopell/SchoologyPlus/blob/master/src/scripts/pages/home.ts)). That is almost exactly Apex Scholar's goal, already running against real student accounts.

Graded state and exceptions come from `GET /users/{user_id}/grades`. Its documented exceptions are 1 for excused and 2 for incomplete, and when an exception is set the grade is NULL ([Grade](https://developers.schoology.com/api-documentation/rest-api-v1/grade/)). Both open-source clients also map an undocumented `exception == 3` to "Missing" ([SchoologyPlus materials.ts](https://github.com/aopell/SchoologyPlus/blob/master/src/scripts/pages/materials.ts); [Raycast Schoology extension](https://github.com/raycast/extensions/tree/main/extensions/schoology)). Combined, these give a defensible status rule:

| Status | Signal | Confidence |
|---|---|---|
| Submitted | latest revision exists and `draft == 0` | High for dropbox assignments |
| Submitted late | that revision has `late == 1` | High |
| Graded | grades row has non-null `grade` and `exception == 0` | High, but only once grades are published |
| Excused / incomplete / missing | `exception` 1 / 2 / 3 | 1 and 2 documented, 3 inferred from two clients |
| Overdue, not submitted | no revision and now > `due` | Apex Scholar's own judgment, not a Schoology flag |

The rule has holes. Assignment `type` can be `assignment`, `discussion` or `assessment`, and only dropbox assignments have revisions ([Assignment](https://developers.schoology.com/api-documentation/rest-api-v1/assignment/)). For Schoology Tests/Quizzes, discussions, LTI tools and `collected_only` columns (which "allow teachers to simply mark materials as completed or not"), the only signal is a grade or exception appearing. That lags the student's actual submission by however long the teacher takes to grade, and it never appears if `auto_publish_grades` is 0 and the teacher hasn't published ([Assignment](https://developers.schoology.com/api-documentation/rest-api-v1/assignment/)). Assignment payloads also show `completed` and `completion_status` fields, but the field tables never define them and the example shows `completion_status` as an empty string. Schoology Plus's FAQ claims to check whether Schoology marks an assignment "completed", but its code actually checks dropbox revisions ([Schoology Plus FAQ](https://schoologypl.us/docs/faq/api)). Those fields must not drive auto-complete until someone tests them on a real student account. The section-level `/completion` endpoint tracks completion-rule progress, not per-assignment submission ([Completion](https://developers.schoology.com/api-documentation/rest-api-v1/section-completion/)). There is also no student write for "mark as done" in Schoology, so the sync can only go one way.

In practice, auto-complete should apply to dropbox assignments only. Grade-appearance should be a second, clearly labelled signal ("graded, so probably turned in"), and every task keeps a manual check-off, as Schoology Plus does. Use the per-user submissions path. No source confirms whether a student token gets a 403 or a filtered list on the all-users `/submissions/{grade_item_id}` path.

## The existing Schoology proxy needs five fixes before it scales

The current function, `netlify/functions/schoology-oauth.js`, gets the fundamentals right. The consumer secret stays server-side, request and access token secrets live in `users/{uid}/private/...` rather than the browser, every action requires a verified Firebase ID token, and the callback is pinned to the app's own origins. Five things still need fixing, and the first is a security issue.

**First, it accepts writes.** Line 329 allows `GET`, `POST`, `PUT` and `DELETE` on any relative path. Schoology's REST OAuth 1.0a has **no read-only scope**: the docs describe no scope granularity, so a student's token carries that student's full permissions ([Authentication](https://developers.schoology.com/api-documentation/authentication/)). With that token, `POST /sections/{id}/submissions/{grade_item_id}/{action}` creates a revision and "will default to submitting this revision" if `draft` is unset. `DELETE` exists for revisions and submission comments, and the API can also post updates, create events and send private messages ([Submissions](https://developers.schoology.com/api-documentation/rest-api-v1/submissions/); [API Documentation](https://developers.schoology.com/api/)). A bug, an XSS in the app, or a compromised Firebase session could therefore submit, delete or message on a student's behalf. Read-only has to be enforced in the proxy: allow `GET`, plus `POST /multiget`, which is a read batch of up to 50 URLs ([Multi-get](https://developers.schoology.com/api-documentation/rest-api-v1/multi-get/)), and reject everything else. A path allowlist (`/users/me`, `/users/{uid}/sections`, `/users/{uid}/grades`, `/sections/{id}/assignments`, `/sections/{id}/grade_items`, `/sections/{id}/submissions/{gid}/{uid}`, `/users/{uid}/updates`, `/recent`, `/multiget`) is the cheap second layer. The file's header comment (lines 14-22) also still describes token secrets round-tripping through the browser, which the code no longer does, so it should be corrected.

**Second, it authorizes on the wrong host.** Line 246 sends students to `api.schoology.com/v1/oauth/authorize`. Schoology's guidance is to redirect to the student's own domain (`district.schoology.com` or a custom domain like `lms.schoolname.org`). Authorizing on the generic host risks tying tokens "with the wrong user" on shared lab computers, and the student has to be logged in at that domain, which for SSO districts means going through the district identity provider ([Handling Domains](https://developers.schoology.com/app-platform/handling-domains/); [Authentication](https://developers.schoology.com/api-documentation/authentication/)). gunn.one does this with a "Find My School" picker that redirects to `https://{school-domain}/oauth/authorize` ([gunn.one/grades](https://gunn.one/grades)). Apex Scholar should collect and store the student's Schoology domain at connect time. Signed REST calls still go to `api.schoology.com`.

**Third, `/users/me` probably fails silently.** `v1/users/me` responds with a 303 redirect, and following it with the same nonce and timestamp produces "401 Duplicate timestamp/nonce combination". The fix is to re-sign before following ([Authentication](https://developers.schoology.com/api-documentation/authentication/)). `callSchoology` uses default `fetch`, which follows redirects with the original `Authorization` header, and the profile lookup is wrapped as "best-effort". The likely result is that `schoologyUid` is stored as null, which would break every `/users/{uid}/...` call downstream. Verify this with one real connection, then use `redirect: 'manual'` and re-sign the `Location` URL.

**Fourth, tokens expire after 90 days and nothing handles it.** Since June 2025, "OAuth1 access tokens will have a maximum lifetime of 90 days," and after that calls fail with 401 until the user re-authorizes ([Schoology API authentication update](https://developers.schoology.com/api-documentation/important-api-authentication-update/)). The function stores `connectedAt` but never checks it. It should prompt re-connection around day 80, and on any 401 it should mark the integration inactive and fall back to iCal.

**Fifth, cross-school access needs Schoology's approval.** The same notice says "apps must be approved by Schoology to access data from other schools. Unapproved apps will receive a 401 error." Apps that are "unpublished or available only within the school will continue to access users within the same school without changes," and App Center apps are unaffected ([Schoology API authentication update](https://developers.schoology.com/api-documentation/important-api-authentication-update/)). The path is the App Publisher at `app.schoology.com/apps/publisher` plus a review form. Review "takes up to 1 month," and a reviewer installs and checks the app before publishing it to the App Center ([LTI Apps](https://developers.schoology.com/app-platform/lti-apps/)). The review criteria are not public. It is also unconfirmed whether a district must separately allow an approved app, but role permissions such as "Access to app center" and per-app access suggest districts can block it ([PowerSchool: Search, apps, and API permissions](https://uc.powerschool-docs.com/en/schoology/latest/search-apps-and-api-permissions)). Whether gunn.one has this approval is unknown.

Polling should stay modest. There is no official rate-limit document. Schoology Plus throttles to 13 requests per 5 seconds against what it calls a "real limit" of 15 ([SchoologyPlus api.ts](https://github.com/aopell/SchoologyPlus/blob/master/src/scripts/utils/api.ts)), while Raycast claims 50 per 5 seconds ([Raycast Schoology extension](https://www.raycast.com/Visual-Studio-Coder/schoology)). Webhooks ("Event Triggers") are configured by school admins only, so a student-authorized app must poll ([Event Triggers](https://developers.schoology.com/api-documentation/rest-api-triggers-v1/)). A workable loop runs on app open and every 15-30 minutes while the app is active. It fetches `/users/{uid}/grades?timestamp={lastSync}`, which returns only changed grades ([User Grades](https://developers.schoology.com/api-documentation/rest-api-v1/user-grades/)), checks submissions only for open tasks due soon, batches through `/multiget`, and stays under 13 requests per 5 seconds per token.

The personal-key fallback that Schoology Plus and Raycast use is weak. The student pastes their own key and secret, and the app makes two-legged calls. Districts that joined Schoology after **August 4, 2022** have student key creation off by default ([PowerSchool permissions](https://uc.powerschool-docs.com/en/schoology/latest/search-apps-and-api-permissions)), Schoology Plus already ships a "blocked by your school" message ([Schoology Plus FAQ](https://schoologypl.us/docs/faq/api)), and no client has confirmed that personal keys still read their owner's data after June 2025. Storing those secrets server-side would also make Apex Scholar the custodian of a password-equivalent. It should stay out of scope.

## Canvas gives richer data but gates every API path behind a district

Canvas's API is technically the better one for this job, but the approval model makes it far harder for a small team. **Developer keys for Instructure-hosted Canvas "are issued by the admin of the institution,"** and a key works only in the root account that created it ([OAuth2 Overview](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)). The exception is a global key, created by Instructure and "functional in any Canvas account where they are enabled". Each district's root admin still has to switch it on, and new keys default to off. Without that, `/login/oauth2/auth` returns `unauthorized_client` ([Developer Keys](https://developerdocs.instructure.com/services/canvas/oauth2/file.developer_keys); [Community: manage developer keys](https://community.instructure.com/en/kb/articles/661518-how-do-i-manage-developer-keys-for-an-account)). Vendors "may request a global developer key from Instructure," but the notes found no published criteria or timeline for getting one.

The usual student shortcut is closed. Instructure's OAuth docs say "asking any other user to manually generate a token and enter it into your application is a violation of Canvas' API Policy. Applications in use by multiple users MUST use OAuth" ([OAuth2 Overview](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)). Since September 2025, admins can stop students from creating tokens at all. Student tokens now expire within **30 days** ([Canvas Deploy Notes 2026-07-01](https://community.instructure.com/en/discussion/666398/canvas-deploy-notes-2026-07-01)), and UW–Madison, UW Seattle, Cornell, St. Edward's and Missouri have shut student tokens off ([UW–Madison IT](https://it.wisc.edu/academic-technology/learn-uw-news/change-to-student-access-tokens-in-canvas/); [UW Connect](https://uwconnect.uw.edu/it?id=kb_article_view&sysparm_article=KB0034590)). LTI 1.3 does not help either: Assignment and Grade Services only expose line items the tool created itself, not the teacher's real assignments, and the tool still needs an admin install ([OAuth2 Overview – LTI Advantage](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)).

If a district does enable a key, the build is straightforward and similar to the Schoology proxy. Canvas returns no CORS headers to third-party origins. In the research team's own probes on 2026-10-16, preflights against a K-12 district, UW and Harvard returned 404 with no `Access-Control-*` headers, and Instructure's docs assistant itself recommends a proxy ([Instructure docs Q&A](https://developerdocs.instructure.com/services/canvas/basics/file.pagination.md)). Every call therefore goes through a Netlify function. The flow is the standard authorization-code grant on `https://<district>/login/oauth2/auth`. Access tokens last 1 hour, and the original refresh token is reused because refresh responses don't issue a new one. Tokens are tied to a domain, so storage must be keyed by Canvas host ([OAuth2 Overview](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)). Store them the way Schoology tokens are stored now (`users/{uid}/private/canvas`, server-only). Keep a `domain → {client_id, secret}` table for district keys, and request a narrow scope list in `url:GET|/api/v1/...` form. The key also needs **"Allow Include Parameters"** turned on, because scoped tokens otherwise ignore `include[]=submission` and `include[]=total_scores`, which is where status and grades come from ([Developer Keys](https://developerdocs.instructure.com/services/canvas/oauth2/file.developer_keys)). One real-world warning: after a May 1, 2026 Canvas incident, Instructure rotated at least one vendor's global key, which invalidated every user token issued under it ([FeedbackFruits help](https://help.feedbackfruits.com/hc/en-us/articles/35311868629138-Follow-up-do-I-need-to-rotate-any-keys-after-the-May-1st-Canvas-incident)).

Canvas's completion data is cleaner than Schoology's. `GET /api/v1/courses/:course_id/students/submissions` defaults to the calling user ("Students may only list their own submissions") and supports `submitted_since`, so each course needs one incremental call. Each submission carries `workflow_state` (submitted, unsubmitted, graded, pending_review), `submitted_at`, `late`, `missing`, `excused`, `late_policy_status` and `posted_at` ([Submissions](https://developerdocs.instructure.com/services/canvas/resources/submissions)). The done rule is `submitted_at != null`, or a workflow state of submitted, graded or pending_review, or `excused`. Exclude `on_paper` and `none` submission types, because a "graded" state with null `submitted_at` means the teacher entered a grade, not that the student turned anything in. New Quizzes are stored as `external_tool` assignments and "cannot be identified by submission type alone," so they show as done only after the tool posts a result back ([Users](https://developerdocs.instructure.com/services/canvas/resources/users.md)). Two other endpoints are useful. `GET /api/v1/planner/items` returns every item across courses in a date range, with `submissions` status and `planner_override.marked_complete` in one paginated call. `GET /users/self/missing_submissions` lists past-due work with no submission ([Planner](https://developerdocs.instructure.com/services/canvas/resources/planner); [Users](https://developerdocs.instructure.com/services/canvas/resources/users.md)). Unlike Schoology, Canvas lets students write their own "mark as done" through `POST/PUT /api/v1/planner/overrides`, which makes two-way sync possible. Those calls are non-GET, though, and the API policy flags "disproportionately large" non-GET traffic ([Instructure API Policy](https://www.instructure.com/policies/canvas-api-policy)), so v1 should stay read-only.

Without district keys, two Canvas paths remain. The iCal feed needs no approval and covers events and assignments 366 days ahead and 30 days back, up to 1,000 items. It excludes To Do items ([Community: Calendar feed](https://community.instructure.com/en/kb/articles/662797-how-do-i-subscribe-to-the-calendar-feed-using-google-calendar)) and has no status or grades. The feed URL is a bearer secret and should be stored like a token. The second path is a browser-extension companion in the style of BetterCanvas. It makes same-origin `/api/v1` calls on the student's logged-in session, including `include[]=submission` and `/planner/items`, with no token and no developer key ([UseBetterCanvas/bettercanvas](https://github.com/UseBetterCanvas/bettercanvas)). It has run openly for years without reported enforcement. The counterargument is real, though. The API policy prohibits "using our APIs to distribute software or tools that gather information," access through "technologies not approved by Instructure," and use "on behalf of any third-party" ([Instructure API Policy](https://www.instructure.com/policies/api-policy)). An extension that sends Canvas data to Apex Scholar's servers fits those clauses worse than BetterCanvas, which keeps data local. Districts also control extensions on managed Chromebooks, and phones can't run them at all. The extension is an enhancement for some students, not a foundation.

## Both APIs reach far beyond the calendar, with grade-weight gaps

Once authorized, both platforms expose most of what a Bessy or gunn.one-style tool needs. The table below summarizes what a student token can plausibly read. Rows marked unverified need testing on a real student account before any feature depends on them.

| Data | Schoology (student OAuth1 token) | Canvas (student OAuth2 token) |
|---|---|---|
| Courses / sections | `/users/{uid}/sections` ([REST index](https://developers.schoology.com/api-documentation/rest-api-v1/)) | `/api/v1/courses`, with `syllabus_body` ([Courses](https://developerdocs.instructure.com/services/canvas/resources/courses.md)) |
| Assignments + due dates | `/sections/{id}/assignments`, `/grade_items` ([Assignment](https://developers.schoology.com/api-documentation/rest-api-v1/assignment/)) | `/courses/{id}/assignments`, with `bucket` filters ([Assignments](https://developerdocs.instructure.com/services/canvas/resources/assignments)) |
| Submission status | Revisions for dropbox items only | All online types; planner and missing lists |
| Per-assignment grades | `/users/{uid}/grades`: grade, max_points, exception, category_id ([User Grades](https://developers.schoology.com/api-documentation/rest-api-v1/user-grades/)) | Submission `score`/`grade`, hidden until `posted_at` |
| Course / period totals | `final_grade[]` with per-category grade | Enrollment `current_score`/`final_score` per grading period ([Enrollments](https://developerdocs.instructure.com/services/canvas/resources/enrollments)) |
| Category weights | `grading_categories.weight`, `drop_lowest`; student visibility **unverified** | `assignment_groups.group_weight`, drop rules, `apply_assignment_group_weights` ([Assignment Groups](https://developerdocs.instructure.com/services/canvas/resources/assignment_groups)) |
| What-if math | Must be computed locally | Server-side What-If Grades API (writes state, "costly") ([What If Grades](https://developerdocs.instructure.com/services/canvas/resources/what_if_grades.md)) |
| Announcements | `/recent`, `/sections/{id}/updates` ([Updates](https://developers.schoology.com/api-documentation/rest-api-v1/update/)) | Announcements API |
| Materials | Documents, pages, course folders ([Course Folder](https://developers.schoology.com/api-documentation/rest-api-v1/course-folder/)) | Modules, pages, files, discussions |
| Push updates | Admin-only Event Triggers, so poll | Admin-only Live Events, so poll ([Live Events](https://developerdocs.instructure.com/services/canvas/data-services/live-events/overview/file.data_service_introduction.md)) |

Grade calculation is where the two platforms differ most. Schoology's grades endpoint gives per-assignment scores with `category_id`, plus per-period totals broken down by category. The section option `weighted_grading_categories` says whether weights apply, and `grading_categories` documents `weight`, `drop_lowest` and `calculation_type` ([Grading Categories](https://developers.schoology.com/api-documentation/rest-api-v1/grading-categories/); [Course Section](https://developers.schoology.com/api-documentation/rest-api-v1/course-section/)). The open question is whether a student token sees those weights. The grades example shows only `{id, title}` on categories. Raycast reads `weight` and falls back to equal weights, while Schoology Plus scrapes weights from the rendered gradebook. That suggests the API omits them for students at least some of the time ([Raycast Schoology extension](https://github.com/raycast/extensions/tree/main/extensions/schoology); [SchoologyPlus grades.ts](https://github.com/aopell/SchoologyPlus/blob/master/src/scripts/pages/grades.ts)). Teachers can also hide max points on missing work. A Schoology calculator therefore needs a manual weight-entry fallback and should always show "Schoology says X%" next to its own computed number. Canvas exposes weights directly. Its main gaps are unposted scores and courses with `hide_final_grades`, and in both cases the student legitimately can't see the data.

Weigh the grade calculator against Apex Scholar's AP-prep mission before building it. LAUSD banned Schoology Plus in 2023, and petitioners said the stated reason was What-If grades used to mislead parents ([change.org](https://www.change.org/p/unban-schoology-plus)). A grade calculator invites more district hostility than any other feature here, and Bessy, gunn.one and Schoology Plus already offer one. The feature with the clearest AP-prep payoff is auto-completion plus due-date awareness. Second is course materials and announcements as context for AI study tools. That raises its own duty: Instructure's policy requires notifying users about any generative-AI use of Canvas-derived data and labelling AI-generated reports ([Instructure API Policy](https://www.instructure.com/policies/canvas-api-policy)).

## Approvals, privacy law and district blocking set the real ceiling

Every path has a gatekeeper, and the gatekeepers differ by platform:

| Path | Who must approve | What breaks it |
|---|---|---|
| Schoology 3-legged OAuth, own school | Nobody beyond the developer account | 90-day token expiry |
| Schoology 3-legged OAuth, other schools | Schoology App Center review (up to 1 month) | 401 until approved; districts can likely restrict app access |
| Schoology personal key | District role permission (off by default for districts new since 8/2022) | Admin toggle; post-June-2025 behavior unconfirmed |
| Canvas OAuth2 | Each district's root admin (own key, or enabling an Instructure global key) | `unauthorized_client`; global-key rotation |
| Canvas personal token | Prohibited for multi-user apps | Admin kill switch; 30-day expiry |
| Browser extension (either LMS) | None formally | Managed-device extension policies; API-policy wording |
| iCal feed (either LMS) | None | Dates only, no status or grades |

The legal picture is narrower than it first looks, but it is not empty. FERPA binds schools that receive federal funds, not Apex Scholar directly ([studentprivacy.ed.gov](https://studentprivacy.ed.gov/content/family-educational-rights-and-privacy-act)). When a student authorizes access to their own records, the school is not disclosing them, so the risk lands on the district. That is one reason districts block keys and extensions. California's **SOPIPA does apply now**, because "operators do not need to have a contract with a school or district in order to be subject to SOPIPA." Coverage turns on whether a product is designed and marketed for K-12 school purposes, which an AP-prep app is ([FPF SOPIPA At a Glance](https://fpf.org/wp-content/uploads/2016/03/SOPIPA-At-a-Glance.pdf)). Its duties are no targeted advertising, no profiling beyond school purposes, no selling, reasonable security, and deletion on district request ([Mintz](https://www.mintz.com/2014/09/california-sets-the-curve-with-new-regulations-on-collection-and-use-of-student-data/)). NY Ed Law 2-d and an SDPC National Data Privacy Agreement apply only once a district contracts with Apex Scholar or hands it data ([N.Y. Educ. Law §2-d](https://newyork.public.law/laws/n.y._education_law_section_2-d); [privacy.a4l.org](https://privacy.a4l.org/)). Canvas OAuth effectively requires exactly that relationship, so a Canvas rollout means NDPA paperwork district by district. Signing once through a state alliance and reusing it through the SDPC registry is the cheapest route. COPPA's amended rule (compliance date April 22, 2026) matters only if any users are under 13 ([Federal Register](https://www.federalregister.gov/documents/2025/04/22/2025-05904/childrens-online-privacy-protection-rule)).

Vendor terms add their own constraints. Schoology's developer agreement says end-user data is owned by PowerSchool, the user or the school, bans selling it, and requires **written permission to store data outside the US**. That makes Apex Scholar's Firestore region worth checking. The agreement also bans marketing to Schoology users without approval and lets PowerSchool terminate on 3 days' notice ([Schoology Developer Terms](https://developer.schoology.com/terms/)). Instructure's API policy treats enrollments and grades as private information "protected by law" and says "don't surprise Customers or Users". It also requires apps to outline their actions at registration ([Instructure API Policy](https://www.instructure.com/policies/canvas-api-policy)). Districts are now quicker to close API doors. One 2026 explainer ties districts' gating of Schoology API access to the early-2025 PowerSchool breach ([Carly blog](https://www.usecarly.com/blog/claude-schoology-integration/)), and a March 2025 class action alleges that Instructure's APIs expose child-specific data to third parties ([National Law Review](https://natlawreview.com/article/edtech-and-privacy-student-information-case-study)). Both point in the same direction: minimize what gets stored. For auto-complete, the server needs only assignment ID, course, due date and a submitted flag. Keep scores client-side if a calculator ever ships, as gunn.one does in `localStorage` ([gunn.one/grades](https://gunn.one/grades)). Never collect SSO passwords.

## A four-phase plan for a small team

The plan front-loads what is fixable in code, starts the slow approvals early, and defers the features with the worst risk-to-value ratio.

| Phase | Timing | Work | Exit criterion |
|---|---|---|---|
| 0. Harden | 1 week | GET-only proxy plus `POST /multiget` and a path allowlist; authorize on the student's own domain; re-sign on 303; 90-day expiry prompt and 401 fallback to iCal; fix stale header comment; update privacy policy for SOPIPA and AI use; confirm Firestore region | No write call can reach Schoology; reconnect flow tested end to end |
| 1. Schoology auto-complete | 2-4 weeks, approval in parallel | Map iCal tasks to API assignment IDs; per-user submission check for dropbox items; graded/exception signal for others; manual override; polling on open plus every 15-30 min under 13 req/5 s. Submit to App Center review on day one | Works for own-school students; App Center decision received |

Phase 1 depends on a short test list that only a real student account can settle. It needs to confirm that `/users/me` returns a uid once redirects are re-signed, that the per-user submissions path works with a student token, and what `completed` and `completion_status` actually mean. It also needs to check whether `/users/{uid}/grades` includes category `weight` for students, and how the personal-key path behaves after June 2025, if it's worth knowing at all. Canvas has a parallel open question: whether planner items are visible to students in every account configuration. The biggest strategic unknown is PowerSchool's App Center review. If it comes back negative, Schoology auto-complete stays limited to one school, and Apex Scholar is in the same position on both platforms: iCal plus manual check-off for everyone, with API sync only where a school has said yes.

## Conclusion

Today's integration is weaker than it looks. The OAuth proxy is well built for secrecy but grants a student's full write power through a function meant only to read, and the June 2025 rules mean it probably cannot serve most of the students it is meant for until Schoology approves the app. The constraint is not technical. Both APIs expose submission status, grades and weights. What limits Apex Scholar is who must say yes, and on both platforms that is increasingly an institution rather than the student. A student study app's durable advantage is therefore not a better grade calculator, which incumbents already offer and districts actively resent. It is reading the minimum data needed to make an AP study plan aware of real coursework, and showing districts and vendors a narrow, read-only, data-minimized footprint that makes saying yes easy.

The sequencing matters more than the feature list. The App Center review and any Instructure global-key request run on someone else's clock, so filing them in week one costs nothing and removes the longest dependency. Every hour spent instead on grade math or a companion extension before those answers arrive is spent on the features most likely to be blocked.
