# Existing student tools for Schoology/Canvas grade and assignment data, and the policy/risk landscape (as of Oct 2026)

Research date: 2026-10-16. "Source inspection" means I read the tool's public GitHub source or the JS bundle its site serves. Anything I could not verify is marked "not public" or listed under Gaps.

## Q1. How do existing tools (Bessy, gunn.one, Schoology Plus, Canvas tools) get the data, what do they show, and what went wrong?

### Takeaway
The tools use four different methods. Schoology Plus reads the student's **personal Schoology API key** off the `/api` page and also modifies the grades page in the browser. gunn.one uses Schoology's official **three-legged OAuth 1.0a**, with a school picker. BetterCanvas makes **same-origin Canvas REST calls from a content script, using the student's logged-in session cookie**. Bessy is a closed-source mobile app that keeps "authentication tokens" on the device, and how it gets them is not public. The failures reported so far all come from districts: LAUSD banned Schoology Plus, and schools block students' API keys. Nobody has reported a vendor takedown.

### Cited Findings

**Schoology Plus (browser extension, open source)**
- Its grade features: letter grades for classes that don't show them, point totals for each category, how many points sit above the next-lower letter grade and how many are needed for the next-higher one, and per-assignment percentages. What-If grades recalculate category and class grades with weights applied. You can add simulated assignments, calculate the minimum score needed on an assignment such as a final, and simulate dropped grades. It also sends desktop notifications for new grades, shows check marks on submitted upcoming assignments, and supports custom grading scales per course — [Schoology Plus README](https://github.com/aopell/SchoologyPlus)
- How it authenticates (source inspection): on the Schoology `/api` page, the extension reads the `edit-current-key` and `edit-current-secret` fields, saves them as `ApiKey`/`ApiSecret` in extension settings, and redirects home. It then calls `https://api.schoology.com/v1/...` with an `OAuth realm="Schoology API",oauth_consumer_key=...,oauth_signature_method="PLAINTEXT"` header, which is two-legged OAuth using the student's personal key (`src/scripts/pages/api-key.ts`, `src/scripts/utils/api.ts`) — [aopell/SchoologyPlus](https://github.com/aopell/SchoologyPlus)
- The consent screen says the API key is needed for "What-If Grades, Assignment Checkmarks, Quick Access, Courses in Common" and promises never to "Collect or store any personal information" or "Have access to your account's password" (source inspection, `api-key.ts`) — [aopell/SchoologyPlus](https://github.com/aopell/SchoologyPlus)
- The code handles districts that block the key. It shows the message "This feature requires access to your Schoology API Key, which has unfortunately been blocked by your school" and disables editing after 403s (`src/scripts/pages/grades.ts`) — [aopell/SchoologyPlus](https://github.com/aopell/SchoologyPlus)
- The FAQ says the key is used for data "that Schoology stores but doesn't show on the website," including whether Schoology marks an assignment completed. When a school blocks the key, What-If Grades, Assignment Checkmarks, Quick Access and Courses In Common stop working, but themes and percentage display still work. Its advice is to ask the district, because the block "may have been unintentional" — [Schoology Plus API FAQ](https://schoologypl.us/docs/faq/api)
- Maintenance: last push 2024-09-16, 126 stars, not archived (GitHub API, checked 2026-10-16) — [aopell/SchoologyPlus](https://github.com/aopell/SchoologyPlus)
- A district banned it. A March 2023 petition says LAUSD banned Schoology Plus among several extensions so students couldn't use "What If Grades" to mislead parents; 110 supporters, closed. The page doesn't say how the ban was enforced — [change.org: Unban Schoology Plus](https://www.change.org/p/unban-schoology-plus). A second LAUSD petition (March 17, 2023) has 1,308 supporters and is marked "Victory" without saying what changed — [change.org: Unban Schoology Plus for students LAUSD](https://www.change.org/p/unban-schoology-plus-for-students-lausd)

**gunn.one ("One — Schoology Grade Calculator and Visualizer")**
- The live site is a Next.js app titled "One - Schoology Grade Calculator," with a footer link to tttm.us and no named author — [gunn.one](https://gunn.one)
- How it authenticates (source inspection of the bundle served at gunn.one/grades on 2026-10-16): a "Continue with Schoology" button opens a popup to `/oauth?token=…`. The page offers "Find My School" (a search of Schoology schools with a default domain of `app.schoology.com`) or a shortcut "PAUSD Login" button for `pausd.schoology.com`. It then redirects to `https://{school-domain}/oauth/authorize?oauth_token=…&oauth_callback={origin}/callback?domain=…`. That is Schoology's **three-legged OAuth 1.0a** flow, so the student never gives gunn.one a password — [gunn.one/grades](https://gunn.one/grades)
- The bundle also calls server endpoints `/auth/verify` and `/auth/logout`, and caches each section's grades in the browser's `localStorage` (`grades-{sectionId}`), which logout clears (source inspection) — [gunn.one/grades](https://gunn.one/grades)
- Public repos named gunn.one exist: [mangostudios747/gunn.one](https://github.com/mangostudios747/gunn.one) (2022, "Gunn.One: The Dashboard," Nuxt 3/GraphQL/Passport, no Schoology code found) and [dylanelu/gunn.one](https://github.com/dylanelu/gunn.one) (2023, a stock Next.js template README). Neither appears to be the current grade calculator, so **the current source is not public**.

**Bessy ("Better Schoology"; iOS, and formerly Android)**
- It shows Schoology or Infinite Campus grades, with What-If grades and a final-grade calculator. The developer is listed as Free Apps LLC — [App Store listing](https://apps.apple.com/ca/app/bessy-schoology-grades/id6445881079)
- The creator is Armaan Aggarwal of Dougherty Valley HS (Wildcat Tribune, April 30, 2025). He built a prototype in September 2022 and released it in December 2022. It started because teachers hid Spanish grades, and he "found a way" to reveal them. Features: What-If, final-grade calculator, widgets, notifications. When DVHS moved from Schoology to Google Classroom for 2024-25 the app crashed, so he added safeguards. The article doesn't say how it gets data — [Wildcat Tribune](https://thewildcattribune.com/20574/news/senior-armaan-aggarwal-designs-bessy-to-aid-students/)
- The privacy policy says Bessy "stores authentication tokens locally on your device and encrypts them," so it "does not have unfettered access" to accounts. It also says it stores no sensitive data such as grades, and uses Mixpanel, Splitbee and RevenueCat. Passwords, FERPA and COPPA are not mentioned, and there is no effective date — [bessy.io/privacy](https://www.bessy.io/privacy)
- An AppBrain listing reports the Android app was removed from Google Play on Apr 11, 2025. The reason is not given and I did not verify it independently — [AppBrain](https://www.appbrain.com/app/bessy-schoology-more/com.bessy.bessy)

**BetterCanvas / BetterCampus (browser extension, open source)**
- Features: dark mode, a better to-do list, and a GPA calculator with High School 4.0 and Weighted 5.0 (AP/IB) scales, adjustable cutoffs and a target-GPA simulator. It has been renamed BetterCampus — [Chrome Web Store](https://chromewebstore.google.com/detail/fcelpnmkhbolfpgfdnngpgoolnmbhpjo); [repo](https://github.com/UseBetterCanvas/bettercanvas)
- How it authenticates (source inspection, v5.12.6 manifest): it runs a content script on `https://*/*` with only the `storage` permission. It calls same-origin Canvas endpoints such as `/api/v1/courses/{id}/assignment_groups`, `/api/v1/courses/{id}/assignments?include[]=submission&include[]=score_statistics`, `/api/v1/planner/items`, and `/api/v1/dashboard/dashboard_cards`. These ride on the logged-in session cookie. Writes like `/api/v1/planner/overrides`, used to mark items done, send an `X-CSRF-Token` read from the `_csrf_token` cookie. **No token, OAuth or developer key is involved** — [UseBetterCanvas/bettercanvas](https://github.com/UseBetterCanvas/bettercanvas)
- Maintenance: last push 2025-05-07, 254 stars — [repo](https://github.com/UseBetterCanvas/bettercanvas)

**Tasks for Canvas (browser extension)**
- It adds a dashboard sidebar with a weekly to-do list and per-course progress rings. It lists active assignments that have no submission and no grade, lets students mark items complete manually and add custom tasks, and syncs Gradescope. v1.4.4 (Feb 2025) added Blackboard and D2L — [Firefox Add-ons](https://addons.mozilla.org/en-US/firefox/addon/tasks-for-canvas/); [Georgia Cyber Academy support](https://support.georgiacyber.org/hc/en-us/articles/19566194966423-Tasks-for-Canvas-Chrome-Browser-Extension)
- How it reads data: **not verified**. I did not inspect its source.

**Native Canvas features**
- What-If grades: only students can enter them, and they don't change the instructor's records. In the Canvas Student app the steps are Grades → "Show What-If Score," and the scores are not saved. If the instructor hides totals, students can't see totals at all — [Tacoma CC KB](https://tacomacc.teamdynamix.com/TDClient/1903/Portal/KB/ArticleDet?ID=52847); [UBC](https://students.canvas.ubc.ca/what-if-grades-in-canvas/)
- Other session-based extensions: the PrettyCanvas policy says it reads data "through the user's existing Canvas LMS session" (grades, submissions, messages) and does not store the password — [PrettyCanvas privacy](https://sites.google.com/view/prettycanvas-privacy-policy)

### Inferences
- The existing tools fall into two groups. Extensions (Schoology Plus, BetterCanvas, Tasks for Canvas) never need district approval, because they act inside the student's own browser session. Their weak point is that districts can block extensions on managed Chromebooks, as LAUSD did. The one hosted web app with a clear method (gunn.one) uses official three-legged OAuth.
- No public evidence shows PowerSchool or Instructure taking down any of these tools. All the reported friction comes from districts: API keys blocked, an extension banned, or a school switching LMS.
- Schoology Plus's "assignment checkmarks" feature is very close to Apex Scholar's goal 1 (auto-complete when submitted). It shows that the submission/completion flag can be read through the student's own API.

### Gaps
- How Bessy authenticates is not public. "Authentication tokens" could mean OAuth tokens, session cookies captured from an in-app web login, or something else. I found no source that says which.
- I could not tell whether gunn.one's Schoology OAuth app is approved for cross-school access under the June 2025 rule (see Q3). If it isn't, its "Find My School" flow probably fails outside its home school. Its operator is also not public; tttm.us is only a link.
- I found no Reddit or HN threads with specific district blocks of Bessy or gunn.one. The search tool returned none.

## Q2. How do the data-access approaches compare: data available, setup friction, reliability, ToS/legal risk, privacy duties?

### Takeaway
No zero-risk route gives both grades and submission status. Official OAuth is the cleanest legally. On Canvas it needs a developer key issued by each district's admin. On Schoology a cross-school app needs Schoology's approval (since June 2025), and tokens expire after 90 days. Personal tokens or keys are banned for multi-user apps on Canvas and can be switched off by admins on both platforms. Collecting SSO passwords is the worst option. A browser-extension companion that uses the student's own session is the lowest-friction way to get grades and submission status. iCal feeds are frictionless and approval-free, but they carry due dates only.

### Cited Findings

**A. Official API with a district- or vendor-approved app (OAuth)**
- Canvas: "For Canvas Cloud (hosted by Instructure), developer keys are issued by the admin of the institution," and keys belong to the institution that issued them — [Instructure OAuth2 docs](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)
- Canvas: "Applications in use by multiple users MUST use OAuth to obtain tokens," and "Storing a token is in many ways equivalent to storing the user's password" — [Instructure OAuth2 docs](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)
- Canvas practitioners say each institution still controls whether an "inherited" key is turned on. Schools usually run a security review (VPAT/HECVAT) before enabling a third-party app. A community moderator says asking users to create personal tokens for a multi-user app violates Instructure's API policy — [Canvas Community thread](https://community.canvaslms.com/t5/Developers-Group/Canvas-API-Access-Question-Higher-Education/td-p/572723)
- Schoology: three-legged OAuth works by redirecting the user to `{domain}/oauth/authorize?oauth_callback=…&oauth_token=…`, where "the user approves your access." Two-legged consumer keys come from the Integration menu and only for roles that have the "Access Schoology API" permission — [Schoology API Authentication](https://developers.schoology.com/api-documentation/authentication)
- Schoology, from June 25, 2025: OAuth1 access tokens last at most 90 days, and after that requests "fail with a 401." Personal API keys can't access other users' data. "Apps must be approved by Schoology to access data from other schools," and unapproved apps get 401. Unpublished apps, or apps limited to one school, keep access to users in that same school. App Center apps are unaffected. Approval and early opt-in go through Schoology support — [Schoology: Important OAuth/API Authentication Update](https://developer.schoology.com/api-documentation/important-api-authentication-update)
- Data: the Schoology API covers users, courses, enrollments, assignments and grades. This comes from a third-party explainer, not official docs — [Ed.link](https://ed.link/community/what-can-i-do-with-the-schoology-api)

**B. Student personal API key or token**
- Schoology: a PowerSchool moderator says system admins decide which users can generate an API key, so a student must ask the district's Schoology admin. Another student reports that two-legged requests worked once the district enabled it — [PowerSchool Community](https://help.powerschool.com/t5/Community-Forum/REST-API-Access-for-students/m-p/398867) (as summarized by search; the forum now redirects to customercentral.powerschool.com)
- Schoology Plus shows this route in production, and also shows districts blocking it ("blocked by your school") — [Schoology Plus FAQ](https://schoologypl.us/docs/faq/api)
- Canvas: the 2025-09-10 deploy notes added the account setting "Restrict students from creating personal access tokens" and removed the older "Admin Manage Access Tokens" option. The 2025-11-05 notes extended it to observers. Users who also hold an instructor role are exempt. Integrations that use developer keys are unaffected — [Canvas Deploy Notes 2025-09-10](https://community.canvaslms.com/t5/Canvas-Releases/Canvas-Deploy-Notes-2025-09-10/ta-p/654577); [2025-11-05](https://community.canvaslms.com/t5/Canvas-Releases/Canvas-Deploy-Notes-2025-11-05/ta-p/661038); [Community thread](https://community.canvaslms.com/t5/Canvas-Question-Forum/Student-use-of-API/m-p/646466) (setting name and scope as quoted in search summaries; the release-note page body did not render for me)
- Real-world restriction: Ohio State disabled personal access token creation in May 2026. Students still can't create them after instructors got the ability back in August, and tokens now expire within 90 days at most — [OSU IT news, 2026-08-11](https://it.osu.edu/news/2026/08/11/carmencanvas-personal-access-tokens)
- Institutions explain why: a third party holding a token "could also expose sensitive data, such as course enrollment, grades, discussion posts, and student submissions," and University of Missouri blocks all non-admins from generating tokens — [UM System token policy](https://tdx.umsystem.edu/TDClient/66/MOOnline/KB/ArticleDet?ID=2193)

**C. Collecting school SSO credentials (password storage): HIGH RISK**
- Canvas docs treat a stored token as roughly equal to a password and require OAuth for multi-user apps, so taking the actual password is a step past even the prohibited token route — [Instructure OAuth2 docs](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)
- None of the researched tools that disclose their method ask for passwords. Schoology Plus explicitly promises it never has "access to your account's password" — [Schoology Plus source](https://github.com/aopell/SchoologyPlus)
- The Schoology developer agreement requires developers to "immediately inform PowerSchool" of "the appearance of unauthorized access" (§1.3) — [Schoology Developer Terms](https://developer.schoology.com/terms/)

**D. Browser extension that reads the page or calls the API with the session (DOM / same-origin)**
- BetterCanvas does this with no token, using same-origin `/api/v1` calls including `include[]=submission`, which returns submission status — [bettercanvas source](https://github.com/UseBetterCanvas/bettercanvas)
- Schoology Plus mixes DOM changes, such as point totals and percentages, which keep working without the key, with personal-key API calls, which break when blocked — [Schoology Plus FAQ](https://schoologypl.us/docs/faq/api)
- Districts can ban extensions, as LAUSD did with Schoology Plus in 2023 — [change.org](https://www.change.org/p/unban-schoology-plus)
- The Instructure API Policy (effective 12 Aug 2025) forbids "using our APIs to distribute software or tools that gather information" (§3(h)) and using the APIs "on behalf of any third-party" (§2(B)). It requires that data "be considered and treated private information" (§2(C)), and Instructure "may revoke your access tokens" for undue load (§4) — [Instructure API Policy](https://www.instructure.com/policies/api-policy)

**E. iCal feed only**
- Canvas feed: events and assignments from all of a student's calendars, 366 days ahead and 30 days back, up to 1,000 items. To Do items are excluded, and the feed must be re-imported after joining a new course — [Canvas Student Guide](https://community.canvaslms.com/t5/Student-Guide/How-do-I-view-the-Calendar-iCal-feed-to-subscribe-to-an-external/ta-p/331)
- Schoology: Account Settings → "Share Your Schoology Calendar" → Enable gives an iCal link. It only works if the personal calendar has at least one entry, and Google Calendar can take up to 8 hours to update. One student reported they couldn't share a course calendar. Sources are school help desks, not official Schoology docs — [McQuaid help](https://help.mcquaid.org/schoology/linking-calendars); [Meadowbrook](https://meadowbrook.freshservice.com/support/solutions/articles/19000052322-Syncing-Your-Schoology-Calendar-to-a-Google-Calendar-Outlook-iCal-etc-)

**Comparison (summary of the findings above)**

| Approach | Grades / weights | Submission status | Student setup | District approval | Main risks |
|---|---|---|---|---|---|
| Official OAuth (Canvas) | Yes | Yes | One click | **Yes: per-district developer key** | Selling to each district; DPA paperwork |
| Official 3-legged OAuth (Schoology) | Yes | Yes | One click (pick school) | No district step shown, but **Schoology approval needed for cross-school use since 6/2025** | 90-day re-auth; vendor approval process not documented |
| Personal key/token | Yes | Yes | Copy key+secret/token (high friction) | Admin can disable (Schoology permission; Canvas Sept 2025 setting) | Canvas docs prohibit it for multi-user apps; you hold a password-equivalent |
| SSO password collection | Yes (via scraping) | Yes | Type password | None, but bypasses the school | Credential storage, MFA/SSO breakage, likely ToS breach, worst look for a student-privacy review |
| Extension (session/DOM) | Yes | Yes | Install extension | None, but districts can block extensions on managed devices | DOM breakage; API-policy wording; Chrome Web Store review |
| iCal feed | **No** | **No** | Paste URL | None | Due dates only; Canvas excludes To Do; Schoology feed is flaky |

### Inferences
- For goal 1 (auto-complete on submission), iCal alone fails because it has no submission flag. That leaves only two practical routes: OAuth, or an extension that reads the student's session.
- On Canvas, a small team can't realistically get OAuth for all districts, because every district must issue a key. A BetterCanvas-style companion extension is the main viable path. It could post submission status to Apex Scholar, with the student's consent, from the student's own browser.
- On Schoology, gunn.one shows a hosted web app can use three-legged OAuth. The June 2025 rule, though, means a new app probably needs Schoology's approval to serve students outside one school. That process is undocumented and should be expected to involve PowerSchool's own review.

### Gaps
- PowerSchool does not publish how to get approved for cross-school access, and the update page only says "contact Schoology support."
- I could not confirm whether Canvas's iCal feed or Schoology's iCal feed includes anything about submission status (none of the sources say it does).
- The Canvas deploy-note page body did not render. The setting name and observer extension come from search summaries of those official pages and one community thread.

## Q3. What does policy allow (vendor terms, FERPA, SOPIPA, NY Ed Law 2-d, SDPC/NDPA, COPPA), and what can a student-authorized, non-contracted app do?

### Takeaway
FERPA binds schools, not Apex Scholar directly. California's SOPIPA likely **does** apply to Apex Scholar without any school contract, because coverage depends on whether a product is designed and marketed for K-12 school purposes. NY Ed Law 2-d and SDPC data privacy agreements only come into play if a district contracts with Apex Scholar or hands it data. Vendor terms set the practical limits: Schoology's approval rule and Instructure's OAuth requirement and API Policy. COPPA mostly doesn't apply to high schoolers, but the amended rule (compliance date April 22, 2026) applies if any users are under 13.

### Cited Findings
- **FERPA scope:** it applies to "educational agencies or institutions that receive funds from programs administered by the U.S. Department of Education" (statute 20 U.S.C. §1232g, regulations 34 CFR Part 99). Private K-12 schools generally aren't covered — [studentprivacy.ed.gov FERPA](https://studentprivacy.ed.gov/content/family-educational-rights-and-privacy-act); [SPPO FAQ](https://studentprivacy.ed.gov/frequently-asked-questions?page=1)
- **FERPA school-official exception:** a vendor gets records without consent only when it is under the school's "direct control," normally through a contract. Ed-tech that receives student data without being contracted as a school official may cause a FERPA problem *for the school* — [Indiana Univ. registrar summary](https://registrar.indiana.edu/policies/ferpa/student-privacy-students.html); [ManagedMethods](https://managedmethods.com/?p=10960) (secondary sources)
- **SOPIPA (Cal. Bus. & Prof. Code §22584):** "Operators do not need to have a contract with a school or district in order to be subject to SOPIPA." Coverage depends on actual knowledge that the service is used primarily for K-12 school purposes and was designed and marketed for them. General-audience products are excluded — [FPF SOPIPA At a Glance](https://fpf.org/wp-content/uploads/2016/03/SOPIPA-At-a-Glance.pdf); [Cooley 2014](https://ed.cooley.com/2014/10/09/californias-student-online-personal-information-protection-act-is-the-first-state-law-to-comprehensively-address-student-privacy/). Core duties: no targeted advertising, no profiling except for K-12 purposes, no selling, limited disclosure, reasonable security, and deletion on district request — [Mintz 2014](https://www.mintz.com/2014/09/california-sets-the-curve-with-new-regulations-on-collection-and-use-of-student-data/) (official statute text returned 403 to my fetch)
- **NY Ed Law 2-d:** a "third-party contractor" is any entity that receives student data **from an educational agency under a contract or other written agreement**. Agencies must attach the Parents' Bill of Rights to those contracts. Student PII "may not be sold or used for marketing purposes" — [N.Y. Educ. Law §2-d](https://newyork.public.law/laws/n.y._education_law_section_2-d); [FPF 2-d at a glance](https://studentprivacycompass.org/wp-content/uploads/2020/01/NYS-Education-Law-2-d-at-a-Glance_FPF.Playwell.pdf)
- **SDPC NDPA:** a standard district–vendor contract that binds vendors to FERPA, COPPA and state law. One state-alliance signature can be adopted by other districts through the SDPC Resource Registry, and agreements last about 3 years. Sources disagree on the current version: v2.2 (Nov 2025) per EdLaw, v2 (Apr 2024) per WSIPC — [privacy.a4l.org](https://privacy.a4l.org/); [Richland One](https://www.richlandone.org/departments/information-technology/technology-approval-process/national-data-privacy-agreements); [EdLaw NDPA](https://edlaw.eduverse.com/docs/jurisdiction/org/sdpc/ndpa/); [WSIPC](https://wsipc.org/news/version-two-of-sdpcs-national-data-privacy-agreement-is-available)
- **Schoology developer agreement (US, 4/15/2022):** end-user data "shall be solely owned by PowerSchool, the end user, or PowerSchool's customer." Developers may not sell it, must warrant they are "authorized to communicate such end user data," need written permission to store data outside the US, and may not market to Schoology users without approval (§3.2–3.4). Either party can terminate with 3 days' notice (§2), and PowerSchool's liability is capped at $500 — [Schoology Developer Terms](https://developer.schoology.com/terms/)
- **Instructure API Policy (12 Aug 2025):** applies to "individuals authorized by Customers." It bans using the APIs "on behalf of any third-party" and distributing "tools that gather information," requires data be treated as private, and allows token revocation — [Instructure API Policy](https://www.instructure.com/policies/api-policy)
- **Litigation context:** a class action filed March 27, 2025 alleges Instructure's APIs and Live Events give third parties child-specific data. These are allegations, not findings — [National Law Review](https://natlawreview.com/article/edtech-and-privacy-student-information-case-study)
- **COPPA:** the amended rule was published 2025-04-22, took effect 2025-06-23, with a general compliance date of 2026-04-22 — [Federal Register](https://www.federalregister.gov/documents/2025/04/22/2025-05904/childrens-online-privacy-protection-rule)

### Inferences
- When a student logs in through OAuth or an extension to pull their own records, that is the student acting on their own account, not the school disclosing records. So FERPA's school-official rules probably don't bind Apex Scholar directly. The risk lands on the district, which explains why districts block keys and extensions. For students under 18, FERPA rights belong to parents, which is one more reason for parental notice and consent in the app. This is my reading, not ED guidance.
- SOPIPA is the law most likely to bind Apex Scholar right now, because it is a product for AP students. Grade data pulled from Schoology or Canvas would be "covered information." Apex Scholar would need to avoid ads, selling and profiling of that data, keep reasonable security, and delete data on request. Many states have SOPIPA-style laws (not researched here).
- NY 2-d and an NDPA only start to matter if Apex Scholar seeks district adoption, which is also what Canvas OAuth keys require. Signing the SDPC NDPA once in a state alliance is the cheapest way to make that work for several districts.
- Instructure's ban on using the APIs "on behalf of any third-party" makes it unclear whether a vendor-run extension calling Canvas APIs with the student's session complies. BetterCanvas has operated openly for years with no reported enforcement. Even so, an Apex Scholar extension that sends Canvas data to Apex servers fits that clause less comfortably than a purely local tool does.

### Gaps
- I found no ED (SPPO) guidance specifically on student-initiated sharing with a non-contracted app.
- I did not survey state SOPIPA analogs beyond CA and NY, or Illinois SOPPA and Connecticut, which have stricter operator contract requirements.
- The official SOPIPA statute text could not be fetched (403), so the duties listed come from law-firm and FPF summaries from 2014–2016.

## Q4. Which approach is feasible for a small team: grades plus submission status with the least friction and risk?

### Takeaway
Ship in three tiers. (1) An **iCal import** now, for due dates, with no approvals needed. (2) An **optional browser extension companion** that reads submission status and grades from the student's own Canvas or Schoology session and syncs only what goal 1 needs, the way BetterCanvas and Schoology Plus do. (3) **Schoology three-legged OAuth** as the hosted web path, after asking PowerSchool about cross-school approval. Avoid password collection entirely. Avoid asking students to paste Canvas tokens: it is prohibited for multi-user apps and increasingly disabled.

### Cited Findings
- The extension route works in production with no district approval: Canvas same-origin calls return submission data — [bettercanvas source](https://github.com/UseBetterCanvas/bettercanvas). Schoology Plus reads completion status through the student's key — [Schoology Plus FAQ](https://schoologypl.us/docs/faq/api)
- The hosted Schoology OAuth route works in production (gunn.one), but cross-school access needs Schoology approval and tokens last at most 90 days — [gunn.one](https://gunn.one/grades); [Schoology update](https://developer.schoology.com/api-documentation/important-api-authentication-update)
- The hosted Canvas OAuth route requires every institution's admin to issue a key — [Instructure docs](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth)
- Personal tokens: Canvas prohibits them for multi-user apps and added a student-token kill switch in Sept 2025 — [Instructure docs](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth); [Canvas Deploy Notes 2025-09-10](https://community.canvaslms.com/t5/Canvas-Releases/Canvas-Deploy-Notes-2025-09-10/ta-p/654577)
- Districts block extensions and keys (LAUSD 2023, Schoology Plus "blocked by your school") — [change.org](https://www.change.org/p/unban-schoology-plus); [Schoology Plus FAQ](https://schoologypl.us/docs/faq/api)

### Inferences
- **Weakest point of the extension plan:** many AP students use district-managed Chromebooks where IT controls which extensions are allowed, so the extension won't reach everyone. Students on personal laptops or phones (phones can't run desktop extensions) won't get it either. Treat the extension as an enhancement, with iCal and manual check-off as the fallback.
- **Weakest point of grade calculators (goal 2):** LAUSD's stated reason for banning Schoology Plus was What-If grades used "to trick parents." A grade-calculation feature brings the most district hostility of any feature here, and Bessy and Schoology Plus already cover it. Before building it, compare its value to Apex Scholar's AP-prep mission against that risk.
- **Data minimization lowers the SOPIPA and policy surface:** for goal 1, sync only assignment ID, course, due date and a submitted flag. Do grade math in the extension and don't send scores to the server. That matches how Schoology Plus and gunn.one keep grades client-side (in extension storage and localStorage).
- Never store SSO passwords. Districts increasingly require SSO and MFA, so password scraping would also break, and it would rule out any later NDPA or district adoption.

### Gaps
- I have no data on what share of AP students are on managed devices that restrict extensions.
- I found no timeline or criteria for PowerSchool's cross-school app approval, or for Instructure partner or inherited-key eligibility for a small vendor.
